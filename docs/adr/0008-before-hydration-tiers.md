# Every Component is Tier 1 (works before hydration) or Tier 2 (readable before hydration, interactive after)

Server-rendered React pages are interactive only after hydration, so each Component promises one of two things before its JavaScript loads. We follow GOV.UK, whose Service Manual says "Government services should be functional using only HTML" and "Where possible the JavaScript should enhance HTML and CSS that provides the same core functionality", and React, whose `<form>` reference says "Passing a Server Function to `<form action>` allow users to submit forms without JavaScript enabled or before the code has loaded", with `useActionState` "for use on pages with React Server Components with progressive enhancement". ADR 0001 already puts behaviour in native elements, so most Components get Tier 1 for free.

- **Tier 1, works before hydration.** Links (Link, SkipLink, Breadcrumbs, Pagination, Navbar, Sidebar); native Field controls and Form, Field and Fieldset submission; `<details>` Components (Accordion, Disclosure); Overlays opened through `commandfor` (Dialog, AlertDialog, Sheet, Popover, ContextualHelp); every display Component.
- **Tier 2, server-rendered and readable, interactive after hydration.** Components whose keyboard model or state is script: Tabs, Combobox, Command, DropdownMenu, ContextMenu, Tooltip, Toolbar's arrow keys, NumberField, PasswordField's reveal button, SearchField's clear button, DropZone, DateField, DatePicker, Calendar, RangeCalendar, DateRangePicker, TimeField, Tree, Splitter, CopyButton, Table's row selection, TagGroup's remove buttons, ToggleButton, ToggleButtonGroup and Toast. A Tier 2 Component renders its final markup on the server, with no mount gate and no hydration shift, and keeps any native fallback. While scripting is off (`@media (scripting: none)`) it hides each control only its script can run, so nothing looks usable and does nothing; with scripting on, they show from the first paint and work once hydration completes.

Every Field control takes part in its form as a native field does, so it works with `<form action>` and Server Functions in both tiers. It submits its value through `FormData` under its `name`: one entry per value for a multi-value control (a range Slider, a multiple FileTrigger), and `startName` and `endName` for a date range. The entries come from native inputs where they exist, and from hidden inputs otherwise. An uncontrolled Field control returns to its `defaultValue` on its form's `reset` event, since React resets a form after its action: "After the `action` function succeeds, all uncontrolled field elements in the form are reset." A hidden input only script updates makes its control Tier 2, and the tier line says what submits before hydration (NumberField submits its starting value). Where the visible input can stand in, it carries the `name` until hydration, which then moves the `name` to the hidden input: a single-choice Combobox submits the typed text before hydration, and its chosen Item's `value` after. Each Field control's stories prove the submitted `FormData` and the value after a reset.

The tiers are the expected classification, and `apps/ui-next-fixture/test/before-hydration.spec.ts` confirms them on the static export in Chromium: it drives every Tier 1 route with JavaScript off and submits each Tier 1 Field control's native GET form, compares each Tier 2 route's accessibility tree before and after hydration and runs axe on its server HTML, checks that script-only controls hide with JavaScript off, and screenshots every route with JavaScript off. A new Component adds its route there in the same change. A Tier 1 failure is a bug to fix, never a reason to reclassify the Component; until it is fixed, its check stays in the spec marked `test.fail()`. Each Component's TSDoc states its tier in one line, and the Getting started guide explains both tiers.

We rejected server-rendering Tier 2 controls disabled and enabling them after hydration: that is a mount gate, and every control would change its look when hydration completes. An attribute that hydration swaps without changing anything on screen is not a mount gate: which input carries a Combobox's `name`, or whether FileTrigger's native input stays in the tab order.
