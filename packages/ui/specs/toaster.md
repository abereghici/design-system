# Toaster

The region that shows toasts: a "Notifications" landmark at the bottom centre of the viewport that stacks, times, announces and positions every toast the app adds with `toast()`. Mount it once, near the root, inside the UIProvider. It stays above Floating layers, including an open modal Dialog, Sheet, AlertDialog or Command dialog, and stays usable there. What one toast looks like and does is in `toast.md`.

```tsx
import { roRO } from "@platform/ui/locales/ro-RO";
import { Toaster } from "@platform/ui/toaster";
import { UIProvider } from "@platform/ui/ui-provider";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="ro">
      <body>
        <UIProvider locale={roRO}>
          {children}
          <Toaster />
        </UIProvider>
      </body>
    </html>
  );
}
```

Status: draft for brand-owner review (phase 5). No source guide of its own: the Toaster's behaviour is in the Toast guide (`components/Toast/README.md` in the artifact); drafted from it, the prototype's `<ab-toaster>` and the reference libraries.

## Anatomy

Toaster (no element of its own) → Announcers (two visually hidden live regions) + Region (`<section popover="manual">`) → List (`<ol>`) → toasts (`<li>`, `toast.md`).

- **Announcers.** Two visually hidden `<div>`s, always rendered while the Toaster is mounted: `<div role="status" aria-atomic="false">` for polite announcements and `<div role="alert" aria-atomic="false">` for danger. They hold one short `<p>` per toast (Behaviour, Announcements). They sit next to the Region, not inside it, so they exist before the first toast shows.
- **Region.** A `<section aria-label={ariaLabel} aria-keyshortcuts="Alt+T" tabindex="-1" popover="manual">`. Shown (`showPopover()`) while at least one toast exists, hidden when the last one has left, so the landmark is in the page only while it has content. It overrides the UA popover box: no border, padding or background, `overflow: visible`, `inset: auto`, `inset-block-end: toast-offset` (24), centred with `inset-inline: 0; margin-inline: auto`, `inline-size: min(toast-width, 100% - 2 × space-inset-lg)`, and `pointer-events: none` (each toast sets `auto`), so the empty area around the stack never blocks the page (prototype: "bottom-centre stack", `inset-block-end:var(--ab-toast-offset)`, `pointer-events:none`).
- **List.** An `<ol>` holding the toasts newest first, stacked in one grid cell aligned to the block end, so tucked toasts sit behind the front one (prototype `grid-area:1/1;align-self:end`).

## States

| State          | How it shows                                                                   | Exposed as                                                             |
| -------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| empty          | Nothing drawn; no landmark in the page                                         | Region not `:popover-open`                                             |
| showing        | The stack at the bottom centre, above every other layer                        | `:popover-open`                                                        |
| collapsed      | Newest in front; up to two tucked behind, 8 px higher and 5 % smaller per step | Default                                                                |
| fanned out     | Every visible toast fully drawn in a column, newest at the bottom              | `:hover` (fine pointers), `:focus-within`; always under reduced motion |
| paused         | Timers stopped                                                                 | Pointer over the Region, focus inside, or the tab hidden               |
| inside a modal | Same picture, rendered inside the topmost open modal `<dialog>`                | Region is a descendant of `dialog:modal`                               |

## Behaviour

- **Mounted once, rendered in place.** The Toaster subscribes to the toast store with `useSyncExternalStore` (React: "useSyncExternalStore is a React Hook that lets you subscribe to an external store."), with a `getServerSnapshot` that returns no toasts ("It will be used only during server rendering and during hydration of server-rendered content on the client."), so the server HTML and the first client render agree. It renders where it is placed, so it inherits `dir`, `lang` and `data-theme` from the UIProvider (phase-4 contract 1). Mount exactly one: a second Toaster would draw every toast twice (documented rule).
- **Why a manual popover.** The Region must sit above menus, popovers and dialogs, which are all in the top layer, and no `z-index` can reach above that: MDN "The top layer … sits on top of all other layers displayed in a web document."; CSS Positioned Layout 4 "Top layer elements are rendered in the order they appear in the top layer; the last element in the top layer is rendered on top of everything else." `popover="manual"` puts the Region there without the behaviours a toast stack must not have: HTML "manual: Does not close other popovers; does not light dismiss or respond to close requests." Opening an `auto` popover does not close it ("If element's popover attribute is in the Auto state, then this will also close all other Auto popovers"), and MDN's `showModal()` note concerns `popover="auto"` only ("popover="auto" popovers are also dismissed by successful HTMLDialogElement.showModal()"; Dialog spec). So the ported `z-index-toast` is not used by the Toaster (flagged: the top layer replaces the Layer scale here, as the Dialog spec notes for modals). The prototype used `position: fixed` with `z-index: var(--ab-z-index-toast)`, which falls behind any open popover or dialog.
- **Staying on top.** A layer opened after the Region is above it. When a toast is added while the Region is showing and focus is not inside it, the Toaster calls `hidePopover()` then `showPopover()`, which appends the Region to the end of the top layer again (CSS Positioned Layout 4, "To add an element to the top layer": "Append el to doc’s top layer."), so the new toast is never hidden behind a menu opened since (inference: the build ticket shows a toast while a DropdownMenu is open and checks it is visible and pressable). The re-show is skipped while focus is inside the Region, so it never pulls the user's focus.
- **Above a modal dialog.** A modal `<dialog>` makes the rest of the document inert, the Toaster included: HTML "A Document document is blocked by a modal dialog subject if subject is the topmost dialog element in document's top layer. While document is so blocked, every node that is connected to document, with the exception of the subject element and its flat tree descendants, must become inert." Being in the top layer does not help: MDN `inert` "Modal <dialog>s generated with showModal() escape inertness … No other element can escape inertness.", and inert content "Cannot be focused", does not "have click events fired when clicked on" and is "hidden from assistive technologies as they are excluded from the accessibility tree". An Undo shown after a change made inside a Dialog would be visible but unpressable and unannounced. So while a modal is open, the Toaster renders its Announcers and Region inside the topmost one:
  - It tracks open modal dialogs in opening order: on mount from `document.querySelectorAll("dialog:modal")`, then from `toggle` events heard with a capture listener on `document` (dialog `toggle` events are newly available, 2025-09-15; `toggle` does not bubble, and a capture listener on `document` sees it on the way down to the dialog: inference to verify), adding a dialog when it opens and matches `:modal`, removing it when it closes.
  - While the list is not empty it renders through `createPortal(…, topmostDialog)`. React: "A portal only changes the physical placement of the DOM node. In every other way, the JSX you render into a portal acts as a child node of the React component that renders it. For example, the child can access the context provided by the parent tree, and events bubble up from children to parents according to the React tree." The Region is then one of the dialog's "flat tree descendants", so it is not inert, and shown after the dialog it is above it in the top layer. When the last modal closes, it renders in place again. This is the only portal in the design system (judgement call against phase-4 contract 1, which is about layers anchored to a Trigger; the Toaster has none).
  - Changing the portal target remounts the Region, so state that must survive lives in the store, not in components: each toast's remaining time, whether it was announced, whether `ab-appear` fired. Remounted toasts render in place without the entry animation (only a toast's first render carries `data-entering`, the only state that has a `@starting-style`). `Element.moveBefore()` would move the nodes without remounting, but it is limited (webstatus.dev `move-before`: Chrome 133, Firefox 144, no Safari), so it is not used.
  - The Dialog's scripted backdrop dismissal reacts only to presses whose target is the `<dialog>` itself (Dialog spec), so pressing a toast inside the dialog does not close it. Escape inside a toast calls `preventDefault()`, so it dismisses the toast and not the dialog (`toast.md`).
  - The libraries do not face this: none of them builds modals on `<dialog>` + `showModal()`. React Aria marks its region "as a "top layer", so that it: - is not aria-hidden when opening an overlay - allows focus even outside a containing focus scope" (`data-react-aria-top-layer`, `useToastRegion.ts`), and Sonner sets the same attribute; Sonner's author's skill advises "Move `<Toaster />` to the document root, outside any dialog/portal container" for a toast behind a modal, which addresses `z-index`, not native inertness (inference from the HTML text above).
- **Announcements** (spec #1 story 39; contract 6 decision: always-mounted announcers in the Toaster, not per-toast roles). MDN live regions: "Establish the live region before updating its content. Start with an empty live region, then allow time for it to be exposed to assistive technologies before updating its content. If you establish the region with JavaScript (either inserting a new element or adding aria-live to an existing element), defer the content update to a later event-loop task, for example using setTimeout()." MDN `alert` role: "Do not try to dynamically add/generate an element with role="alert" that is already populated with the alert message you want announced - this generally does not lead to an announcement, as it is not a content change." So a toast inserted with `role="status"` already on it (the source's design) may never be heard. Instead, when a toast is first added, the Toaster appends a `<p>` with its Title and Description to the `status` announcer (or the `alert` announcer for danger) in a later task (`setTimeout`), and removes it when the toast leaves. `role="status"` is polite ("Elements with the role status have an implicit aria-live value of polite and an implicit aria-atomic value of true." MDN), `role="alert"` assertive ("Setting role="alert" is equivalent to setting aria-live="assertive" and aria-atomic="true"."); both set `aria-atomic="false"`, so only the added `<p>` is read and not every message still in the announcer (the default `aria-relevant` is "additions text", MDN). When the Announcers remount inside a modal they start empty and toasts already announced are not added again. The visible toasts carry no live role, so nothing is read twice. Library choices, for comparison: Sonner and Base UI make the whole region polite (`aria-live="polite"`, `aria-relevant="additions text"`, `aria-atomic="false"`), and Base UI also inserts a hidden `role="alert"` copy of each high-priority toast; Radix renders a hidden `role="status"` announcer per toast with `aria-live` "assertive" or "polite", filled "in the next frame to ensure toast is announced in NVDA", noting "Toasts are always role=status to avoid stuttering issues with role=alert in SRs."; React Aria gives each toast's content `role="alert"`. Whether `role="alert"` stutters is the screen-reader pass's question (spec #1 "Manual: a short screen-reader pass per component").
- **Stack** (source: "older toasts tuck behind (−8px, −5% scale per step, max 3 visible). Hover or focus fans the stack out."). The Toaster sets on each toast `--index` (0 for the newest; exiting toasts are skipped) and `--offset` (the sum of the heights of the newer toasts plus `toast-stack-gap` each, measured with a `ResizeObserver`), as the prototype's `layout()` does. Collapsed: `translate: 0 calc(var(--index) * var(--ab-toast-stack-gap) * -1)` and `scale` stepping down by `1 − toast-stack-scale` per index, `transform-origin` at the bottom centre, and a tucked toast's content at `opacity: 0`. Fanned out (`:hover` under `@media (hover: hover)`, or `:focus-within`, on the Region): `translate: 0 calc(var(--offset) * -1); scale: 1`, all content visible. The fourth and older toasts get `data-hidden` and `inert` (Base UI: "Limited toasts remain mounted with the HTML `inert` attribute"), so they are neither seen nor tabbable; their timers keep running, and they move forward when a newer toast leaves (Sonner keeps them mounted and hidden too; Ark queues them instead). `sibling-index()` is newly available (webstatus.dev `sibling-count`, low 2026-08-18) but is not used: exiting toasts stay in the DOM and the fan-out needs measured heights anyway (judgement call).
- **Timers pause** for every toast while the pointer is over the Region (`pointerenter` / `pointerleave`), while focus is inside it (`focusin`, and `focusout` whose `relatedTarget` is outside), and while `document.visibilityState` is `"hidden"` (source: "timers pause on hover, focus and hidden tabs"; Sonner pauses on `expanded || interacting || isDocumentHidden`; Radix "Pauses closing on hover, focus and window blur."). Window blur alone does not pause (the source lists hidden tabs only).
- **Alt+T.** A `keydown` listener on `document`: with `altKey` and no Ctrl, Meta or Shift, and `event.code === "KeyT"` or `event.key` "t" (case-insensitive), while at least one toast exists, it calls `preventDefault()`, remembers the focused element and focuses the Region (`preventScroll`). That fans the stack out and pauses the timers; Tab then reaches the newest toast's Action. Source: "Region landmark "Notifications" (Alt+T to focus)"; Sonner "`hotkey = ['altKey', 'KeyT']`" and docs "hotkey … ⌥/alt + T"; Ark "hotkey '['altKey', 'KeyT']' … The hotkey that will move focus to the toast group". `KeyboardEvent.code` is limited (MDN: "This feature is not Baseline because it does not work in some of the most widely-used browsers."): it is a progressive enhancement for macOS, where Option+T produces "†" as `event.key`; where it is missing the `key` check covers other layouts, and the Region is still reached with Tab and landmark navigation, so its absence reads as correct. Firefox on Windows may also open its Tools menu on Alt+T; the build ticket checks what the user sees there (inference).
- **Escape on the Region** (focus on the `<section>` itself, after Alt+T): returns focus to the remembered element and calls `preventDefault()` (Base UI: "Pressing <kbd>F6</kbd> again returns focus to where it was."; Sonner collapses the stack on Escape). Escape inside a toast dismisses that toast (`toast.md`).
- **Focus after a dismissal.** When the focused toast closes, focus moves to the same control in the next toast (older), or to its Dismiss when it has no Action; when no toast is left, to the element focused before focus entered the Region (remembered on `focusin` from `relatedTarget`, or by Alt+T), or nowhere if that element is gone. React Aria: "When a toast is closed, focus moves to the next toast if any. When the last toast is closed, focus is restored to where it was before."
- **Action shortcut** (⌘Z / Ctrl+Z for Undo): bound by the Toaster for the newest toast only (`toast.md`, Behaviour).
- **Client component.** `toaster.tsx` is `'use client'` (state, effects, document listeners).

## Motion

The Region has none of its own: it is shown when the first toast's entry starts and hidden after the last toast's exit ends. The toasts' entry, stack moves and exit are in `toast.md` (Motion).

- **Reduced motion:** the stack is always fanned out (no tuck, no scale), so hover and focus change nothing and only fades remain (decision for contract 10, `toast.md`).
- **Instant exit:** hiding the Region is a top-layer exit, which spike #4 found instant in Firefox and WebKit ("compute `display: none` at once"); it is hidden only after its last toast has finished leaving, so there is nothing left to see and the instant hide reads as correct.

## Keyboard

No APG pattern covers toasts or a notifications area (APG patterns index, https://www.w3.org/WAI/ARIA/apg/patterns/). The Region is a landmark, which screen readers already let users jump to: APG Landmark Regions "Screen readers exploit landmark roles to provide keyboard navigation to important sections of a page." (https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/). The keys inside a toast are in `toast.md`.

| Key                    | Source                                                                                                                                                                  | Here                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Alt + T (anywhere)     | Source "Alt+T to focus"; Sonner `hotkey` "⌥/alt + T"; Ark `hotkey` "'['altKey', 'KeyT']'"; Radix Viewport "F8: Focuses toasts viewport."; Base UI and React Aria use F6 | Focuses the Region while toasts exist; the stack fans out and pauses.                        |
| Tab / Shift + Tab      | Radix "Tab: Moves focus to the next focusable element."                                                                                                                 | From the Region into the newest toast, then older ones; out at either end. No wrap, no trap. |
| Escape (on the Region) | Base UI "Pressing <kbd>F6</kbd> again returns focus to where it was."                                                                                                   | Returns focus to where it was before Alt+T.                                                  |

F6 and F8 are not bound: the source picks Alt+T, and F6 already moves between browser panes (React Aria: "Toast regions are landmark regions that can be navigated using F6 to move forward and Shift + F6 to move backward."; judgement call: one hotkey).

**RTL:** no arrow-key behaviour, so nothing to swap.

## Accessibility

- **Landmark.** A `<section>` with an accessible name is a region landmark: APG "The HTML section element defines a region landmark when it has an accessible name (e.g. aria-labelledby, aria-label or title)."; ARIA 1.2 "Authors MUST give each element with role region a brief label that describes the purpose of the content in the region." It exists only while toasts show (a hidden popover is `display: none`), which keeps an empty landmark out of the page summary (MDN `region`: "Use sparingly!").
- **Hotkey discoverable.** `aria-keyshortcuts="Alt+T"` on the Region (MDN: "exposes the existence of the shortcut to assistive technologies so the presence of the shortcut can be communicated to its users"). Radix: "It is up to you to ensure the discoverability of the hotkey for keyboard users." The docs page also lists it.
- **List semantics.** The `<ol>` tells a screen-reader user how many toasts there are; `inert` keeps hidden ones out of that count.
- **Announcements** as above: polite for every toast, assertive for danger, never moving focus (WCAG 4.1.3, `toast.md`).
- **Focus** is never moved by a toast appearing; only Alt+T (the user's own key) and a dismissal of the focused toast move it.
- **Contrast:** nothing of its own (the Region draws nothing).
- **More contrast / Forced colors / Reduced transparency:** nothing of its own; each toast handles them (`toast.md`). The Region has no border or fill to restore.

## RTL

Logical properties only (`inset-block-end`, `inset-inline`, `margin-inline: auto`); the stack is centred, so it is the same in both directions. The Region inherits `dir` in the top layer, also inside a modal (spike #4 §4: "native top-layer elements keep their DOM parent's direction").

## Component tokens

No `toaster` Dictionary word: the Toaster uses the toast tokens (`toast-offset`, `toast-width`, `toast-stack-gap`, `toast-stack-scale`, `toast-stack-duration`, `toast-stack-easing`; `toast.md`) and `space-inset-lg` directly for the side margin. No new tokens. `z-index-toast` is not used (Behaviour: the top layer decides the order).

## Author-written text

None. The region's `aria-label` and each toast's `closeLabel` are required by type; toast titles, descriptions and action labels are the author's.

## Feedback events

None of its own. Each toast dispatches `ab-appear`, `ab-confirm` and `ab-dismiss` from its `<li>` (`toast.md`); they bubble to `document` both in place and from inside a modal dialog.

## What the build ticket checks

Stated as what a user, assistive technology or consumer perceives (user-centric rule):

- A `toast()` call from a page's client component shows a toast in the Toaster mounted in the layout, in `apps/ui-next-fixture` (one store across the two subpaths), and a route that only calls `toast()` ships no Toaster code.
- The Region is a landmark named "Notifications" (and "Notificări" with `roRO`) only while toasts show; it exposes `aria-keyshortcuts="Alt+T"`; it lists the visible toasts, newest first.
- A toast added while a modal Dialog is open is visible above it, its Action and Dismiss are pressable and reachable with Tab inside the dialog, Escape on it dismisses the toast and leaves the dialog open, and the dialog's own Escape and backdrop still close the dialog. The same toast is visible and pressable while a DropdownMenu is open.
- Announcements: a status message for a neutral toast and an alert for a danger one, each once, including a toast added in the same task the Toaster first mounts and one added while a modal is open (accessibility tree plus the manual screen-reader pass).
- Timers: a toast is gone after its duration; still visible past it while hovered, while focus is inside the Region, and while the tab is hidden; gone once that ends and its remaining time has passed. A danger toast stays 6 s.
- Alt+T moves focus to the Region (also on macOS with Option+T) and Escape returns it; dismissing the focused toast moves focus to the next toast, then back to where it was.
- With four toasts, three are visible and Tab reaches only those; hover or focus shows all three fully (screenshots, also under reduced motion where they are always fanned out).
